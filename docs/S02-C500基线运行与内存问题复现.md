> 文档状态：`部分验证`
>
> 所属阶段：阶段 1｜租赁 C500 环境、精度与重复基线预验证
>
> 实验时间：2026-09-30 至 2026-10-01（UTC+8）
>
> 证据边界：市场租赁 MetaX C500 64GB，不是组委会已书面认可的正式环境

这份文档复现第一个可完整交付的 C500 阶段性成果：在不改动官方服务参数、精度配置和吞吐 workload 的前提下，解决评测客户端与推理服务共享 64 GiB 宿主内存时触发 cgroup OOM 的问题，并完成 MATH-500 Level 3 以及 4K/1K、16K/1K 各四轮基线。正文从软硬件身份、内存根因、客户端隔离命令、原始结果与回滚边界串起完整证据链。

## 1. 这次成果在什么环境中完成

[租赁诊断] 本轮使用单张 MetaX C500，`mx-smi` 报告 65,536 MiB 设备显存，驱动为 3.8.30，MACA 为 3.7.0.38。宿主可见内存和 cgroup 上限均为 64 GiB，并且没有 swap；因此“GPU 显存 64GB”与“推理服务和客户端可共享的宿主内存”是两个不同容量边界。这不是官方指定卡型有问题，而是该租赁容器的客户端进程也会计入同一宿主 cgroup 限额。

| 身份项 | A0-10 / A0-12 实际值 |
|---|---|
| GPU | 1× MetaX C500，65,536 MiB |
| 宿主内存 | 64 GiB，cgroup `memory.limit_in_bytes=68719476736`，无 swap |
| Python / Torch / Triton | Python 3.12.11；`torch==2.8.0+metax3.7.0.7`；`triton==3.0.0+metax3.7.0.7` |
| 推理与评测 | `vllm==0.24.0+empty`；`vllm-plugin-fl==0.3.0rc1.post1+g13eb9be69`；`flag_gems==5.3.5`；`evalscope==1.11.1` |
| 开发仓库 | `vllm-plugin-FL@13eb9be69ecc5b5ca4f79c44e9ee40081eaa1bf0`；`FlagGems@a7620cc191a0b42e040194622c5758b22a7a25dc` |
| vLLM 参考仓库 | 本地只读 `vllm@ee0da84ab9e04ac7610e28580af62c365e898389`；基线服务实际使用容器安装的 vLLM 0.24.0，响应指纹为 `vllm-0.24.0-74db1639` |
| 实际导入边界 | 服务日志确认 vLLM 与 `vllm_fl` 来自 `/opt/conda/lib/python3.12/site-packages/`，dispatch 配置为该目录下 `vllm_fl/dispatch/config/metax.yaml` |

[源码事实] 基线时 `/data/flagos/src/` 中的开发 checkout 已固定到上表 SHA，但运行时仍是 site-packages 中的已安装包，不能把后续 M1 诊断服务的 `/data` 源码激活状态倒写到本基线。`flag_gems` 的安装版本 5.3.5 已记录，但 A0-10/A0-12 没有单独归档其 `__file__` 输出，因此不把本地 checkout 路径冒充为实际 import 路径。

## 2. 为什么 64GB C500 仍会出现 OOM

[实验结论] A0-07 启动的服务参数与后来成功运行保持一致，但当 EvalScope 客户端也可见 GPU 时，cgroup 的 `oom_kill` 计数从 1 增到 2，EngineCore 退出，后续请求只能得到连接失败。该失败发生在宿主/cgroup 内存边界，不是 C500 的 65,536 MiB 设备显存不符合赛题，也不是模型精度失败。

[分析假设] 根因模型是：GPU 可见的客户端会加载平台插件与相关运行时，与已占用大量宿主内存的 API Server/EngineCore 叠加后超过 64 GiB cgroup 上限。不应为规避这个问题而改小 `--gpu-memory-utilization`、缩短 workload 或改动服务命令；只需要让不执行模型计算的客户端不可见 GPU，服务仍保持 GPU 可见且 `VLLM_PLUGINS=fl`。

EvalScope 是通过 `http://127.0.0.1:9031` 调用 OpenAI 兼容 API 的客户端，它不需要直接使用 C500。benchmark wrapper 的子进程会导入 vLLM CLI，因此除了把客户端 `CUDA_VISIBLE_DEVICES` 设为空，还要仅对该客户端命令把 `VLLM_PLUGINS` 设为空，避免客户端激活 FL 平台插件。这两个都是 shell 行内变量，不会改变另一个 shell 中的服务环境。

## 3. 如何复现精度与吞吐基线

1. 在服务端 shell 进入 `/workspace`，只对该 shell 设置 `VLLM_PLUGINS=fl`，然后使用赛题 C500 原始参数启动服务。预期日志显示模型 BF16、`max_seq_len=131072`、`vendor.metax` 和 9031 端口可用；A0-10/A0-12 实际均使用同一个未改参的服务。

```bash
cd /workspace
export VLLM_PLUGINS=fl
vllm serve /workspace/MiniCPM5-2B \
  --port 9031 \
  --served-model-name minicpm \
  --gpu-memory-utilization 0.85 \
  --max-model-len 131072
```

2. 在另一个客户端 shell 仍从 `/workspace` 运行完整 Level 3。`CUDA_VISIBLE_DEVICES=` 只对这一条 EvalScope 命令生效；实际配置回填为 seed 42、`temperature=1.0`、`top_p=0.95`、`max_tokens=32768`、单次 repeats，不应改写这些值。

```bash
cd /workspace
CUDA_VISIBLE_DEVICES= evalscope eval \
  --model minicpm \
  --api-url http://127.0.0.1:9031/v1/chat/completions \
  --api-key EMPTY \
  --eval-type openai_api \
  --datasets math_500 \
  --dataset-args '{"math_500": {"dataset_id": "/workspace/evalscope-datasets/math_500", "subset_list": ["Level 3"]}}' \
  --eval-batch-size 8 \
  --timeout 3600 \
  --generation-config '{"temperature": 1.0, "top_p": 0.95, "max_tokens": 32768}' \
  --work-dir /workspace/evalscope-datasets/level3 \
  --ignore-errors
```

3. 精度完成后保持服务不变，再在客户端 shell 运行官方 wrapper。两个空值变量都只作用于客户端命令：`CUDA_VISIBLE_DEVICES=` 隐藏 GPU，`VLLM_PLUGINS=` 禁止 benchmark CLI 激活 FL 平台插件；服务仍然 GPU 可见并保持 `VLLM_PLUGINS=fl`。

```bash
cd /workspace
CUDA_VISIBLE_DEVICES= VLLM_PLUGINS= \
python3 /workspace/vllm-plugin-FL/benchmarks/benchmark_throughput_serve.py \
  --model /workspace/MiniCPM5-2B \
  --served-model-name minicpm \
  --port 9031 \
  --test-cases '[[4096,1024,64,256],[16384,1024,64,128]]'
```

4. 每个客户端任务前后在该租赁容器读取 cgroup v1 的 OOM 计数，并保存 wrapper 与结果文件哈希。预期是 `oom_kill` 不增、Level 3 有 105 个完整结果、两个场景各四轮全部 `SUCCESS`；A0-10 和 A0-12 均满足这三项。

```bash
cat /sys/fs/cgroup/memory/memory.oom_control
sha256sum /workspace/vllm-plugin-FL/benchmarks/benchmark_throughput_serve.py
```

## 4. 实际结果说明了什么

[实验结论] A0-10 共请求 105 题，105 题全部成功，无 error 和 incomplete；得分为 `0.9714`，即 102/105，高于 0.95 门槛。运行前后 `oom_kill` 均为 2，说明客户端隔离后没有新的 cgroup OOM。这是租赁 C500 的预验证结果，不是官方精度验收。

[实验结论] A0-12 的 wrapper SHA-256 为 `0813eba574e9d1eb50c297c515baa426da1bcb61ce8c78a398b482f246005565`，内部保持 `RUNS=4` 和 `SKIP_FIRST=1`。原始八轮全部成功，`oom_kill` 前后仍为 2；下表的吞吐、TTFT、TPOT 和 ITL 来自后三轮官方 summary，标准差与 CV 仅对后三轮 total tok/s 计算。

| 场景 | 四轮 total tok/s | 后三轮 total tok/s | CV | 成功请求 | output tok/s | Mean / median / P99 TTFT | Mean TPOT / ITL |
|---|---|---:|---:|---:|---:|---|---|
| 4K/1K，并发 64 | 5059.42 / 4715.71 / 5081.63 / 4717.72 | 4838.35 ± 210.69 | 4.35% | 每轮 256/256 | 967.67 | 3290.92 / 1007.04 / 19278.57 ms | 62.71 / 62.71 ms |
| 16K/1K，并发 64 | 7024.49 / 6998.73 / 6998.73 / 7003.24 | 7000.23 ± 2.60 | 0.04% | 每轮 128/128 | 411.78 | 27344.07 / 4363.14 / 102585.28 ms | 124.93 / 124.93 ms |

4K 的 4.35% CV 表明当次运行波动明显，所以 4838.35 tok/s 只能作为这台租赁实例的初步对照，不能用于判定不足 1% 的优化。16K 的后三轮更稳定，但仍受租赁平台身份边界限制。本轮没有采集 profiler trace，也没有可用于报告的 GPU 显存峰值或宿主内存峰值；server log 中的 KV Cache 使用率不能冒充总峰值。Prefill、混合阶段、稳态 Decode 和收尾时间窗也尚未分离归因。
