# S02：C500 基线运行与内存问题复现

> 文档状态：`部分验证`
>
> 所属阶段：阶段 1｜租赁 C500 环境、精度与重复基线预验证
>
> 实验时间：2026-09-30 至 2026-10-01（UTC+8）
>
> 平台条件：市场租赁 MetaX C500 64GB，不是组委会已书面认可的正式环境

这份文档复现租赁 C500 上的客户端内存隔离与唯一已保留的 M1 代码改动：先解决评测客户端触发的宿主内存 OOM，再解释 Prefill 累计长度为何可以跨 42 层复用，最后核对两次精度评测和 4K/16K 重复吞吐。A0 只表示组委会公布的官方基线，B1 表示本轮租赁 C500 的 M1 预验证；首次吞吐运行覆盖完整双场景，后续各场景单独复测只用于检查稳定性。租赁结果和官方成绩不能混同，内部未改原版运行也不是第三类公开结果。

## 1. 这次成果在什么环境中完成

[租赁诊断] 本轮使用单张 MetaX C500，设备显存为 65,536 MiB，驱动为 3.8.30，MACA 为 3.7.0.38。宿主可见内存和 cgroup 上限均为 64 GiB，并且没有 swap；因此“GPU 显存 64GB”与“推理服务和客户端可共享的宿主内存”是两个不同容量边界。这不是官方指定卡型有问题，而是该租赁容器的客户端进程也会计入同一宿主 cgroup 限额。

[源码事实] B1 加载 `/data/flagos/src/vllm-plugin-FL` 中的 M1 提交 `47882ba2585dafdec92f06aff8ceb8af1de54630`。唯一生产代码改动位于 `vllm-plugin-FL/vllm_fl/dispatch/backends/vendor/metax/impl/attention/flash_attn.py`。以下直接展示修改后实际使用的代码片段，不使用差异标记；未列出的代码保持原样。Attention 数学、KV Cache 内容、模型输入和官方服务参数均未改变。

`FlashAttentionMetadata` 增加一个可选字段，保存当前调度步的 Prefill 累计长度：

```python
    causal: bool = True
    prefill_cu_seq_lens: torch.Tensor | None = None
```

该字段默认是 `None`，因此不满足复用条件的路径仍可沿用原有计算方式。它保存的是 GPU tensor，供同一步的各层 Attention 使用。

`FlashAttentionMetadataBuilder.build` 在满足条件时只计算一次前缀和，并放入 metadata：

```python
prefill_cu_seq_lens = None
if num_prefills > 0 and not use_cascade and self.dcp_world_size == 1:
    prefill_cu_seq_lens = torch.cat(
        (prefill_seq_lens.new_zeros(1), prefill_seq_lens)
    ).cumsum(dim=0, dtype=torch.int32)
```

这里的输入是当前调度步的 `prefill_seq_lens`，输出是以 0 开头的累计长度。builder 在创建 `FlashAttentionMetadata` 时实际传入 `prefill_cu_seq_lens=prefill_cu_seq_lens`；只在非 cascade、单 DCP 分组且存在 Prefill 时创建 tensor，其他路径保持 `None`，同一步各层读取同一个结果。

`FlashAttentionImpl.forward` 优先复用 metadata 中的结果；没有预计算结果时保留原有 fallback：

```python
                num_decode_tokens = attn_metadata.num_decode_tokens
                if attn_metadata.num_prefills > 0:
                    cu_prefix_kv_lens = attn_metadata.prefill_cu_seq_lens
                    if cu_prefix_kv_lens is None:
                        cu_prefix_kv_lens = torch.tensor(
                            [0] + attn_metadata.prefill_seq_lens.tolist(),
                            device=attn_metadata.prefill_seq_lens.device,
                            dtype=torch.int32,
                        ).cumsum(dim=0, dtype=torch.int32)
                    output[num_decode_tokens:num_actual_tokens] = (
                        flash_attn_varlen_func(
                            q=query[num_decode_tokens:num_actual_tokens],
                            k=key_cache,
                            v=value_cache,
                            block_table=attn_metadata.prefill_block_table,
                            cu_seqlens_q=attn_metadata.prefill_query_start_loc,
                            cu_seqlens_k=cu_prefix_kv_lens,
                            max_seqlen_q=attn_metadata.max_query_len,
                            max_seqlen_k=attn_metadata.prefill_max_seq_len,
                            softmax_scale=self.scale,
                            causal=attn_metadata.causal,
                            window_size=self.sliding_window,
                            alibi_slopes=self.alibi_slopes,
                            softcap=self.logits_soft_cap,
                            s_aux=self.sinks,
                        )
                    )
```

修改前，`FlashAttentionImpl.forward` 每层都把 GPU 上的 `prefill_seq_lens` 转成 Python 列表，再创建张量并求 cumulative sum；`.tolist()` 会引入设备到主机的同步，42 层重复支付这笔开销。修改后，metadata builder 在当前调度步仅计算一次 `[0, len_1, …]` 的前缀和，所有层读取同一个 GPU tensor；cascade、DCP 等路径仍使用原实现。短请求的定向 Profile 中，Device→Pageable 拷贝由 42 次降为 0 次、`aten::cumsum` 由 42 次降为 1 次，证明改动命中预期路径；这只是机制检查，不能单独当作 16K 端到端收益。`flag_gems` 安装版本为 5.3.5，其本地 checkout 不等于运行时 import 路径。

## 2. 为什么 64GB C500 仍会出现 OOM

[实验结论] 此前租赁环境的诊断实验启动参数与后来成功运行保持一致，但当 EvalScope 客户端也可见 GPU 时，cgroup 的 `oom_kill` 计数从 1 增到 2，EngineCore 退出，后续请求只能得到连接失败。该失败发生在宿主/cgroup 内存边界，不是组委会公布的官方基线结果，也不是 C500 的 65,536 MiB 设备显存不符合赛题或模型精度失败。

[分析假设] 根因模型是：GPU 可见的客户端会加载平台插件与相关运行时，与已占用大量宿主内存的 API Server/EngineCore 叠加后超过 64 GiB cgroup 上限。不应为规避这个问题而改小 `--gpu-memory-utilization`、缩短 workload 或改动服务命令；只需要让不执行模型计算的客户端不可见 GPU，服务仍保持 GPU 可见且 `VLLM_PLUGINS=fl`。

EvalScope 是通过 `http://127.0.0.1:9031` 调用 OpenAI 兼容 API 的客户端，它不需要直接使用 C500。benchmark wrapper 的子进程会导入 vLLM CLI，因此除了把客户端 `CUDA_VISIBLE_DEVICES` 设为空，还要仅对该客户端命令把 `VLLM_PLUGINS` 设为空，避免客户端激活 FL 平台插件。这两个都是 shell 行内变量，不会改变另一个 shell 中的服务环境。

## 3. 如何复现精度与吞吐对比

1. 在服务端 shell 进入 `/workspace`，只对该 shell 设置 `VLLM_PLUGINS=fl`，然后使用赛题 C500 原始参数启动服务。预期服务使用 BF16、`max_seq_len=131072`、`vendor.metax` 并在 9031 端口可用；B1 实际使用未改参的服务。

```bash
cd /workspace
export VLLM_PLUGINS=fl
vllm serve /workspace/MiniCPM5-2B \
  --port 9031 \
  --served-model-name minicpm \
  --gpu-memory-utilization 0.85 \
  --max-model-len 131072
```

2. 在另一个客户端 shell 仍从 `/workspace` 运行完整 Level 3。`CUDA_VISIBLE_DEVICES=` 只对这一条 EvalScope 命令生效；实际配置回填为 seed 42、`temperature=1.0`、`top_p=0.95`、`max_tokens=32768`、单次 repeats，不应改写这些值。

```bash
cd /workspace
CUDA_VISIBLE_DEVICES= evalscope eval \
  --model minicpm \
  --api-url http://127.0.0.1:9031/v1/chat/completions \
  --api-key EMPTY \
  --eval-type openai_api \
  --datasets math_500 \
  --dataset-args '{"math_500": {"dataset_id": "/workspace/evalscope-datasets/math_500", "subset_list": ["Level 3"]}}' \
  --eval-batch-size 8 \
  --timeout 3600 \
  --generation-config '{"temperature": 1.0, "top_p": 0.95, "max_tokens": 32768}' \
  --work-dir /workspace/evalscope-datasets/level3 \
  --ignore-errors
```

3. 精度完成后保持服务不变，再在客户端 shell 运行官方 wrapper。两个空值变量都只作用于客户端命令：`CUDA_VISIBLE_DEVICES=` 隐藏 GPU，`VLLM_PLUGINS=` 禁止 benchmark CLI 激活 FL 平台插件；服务仍然 GPU 可见并保持 `VLLM_PLUGINS=fl`。

```bash
cd /workspace
CUDA_VISIBLE_DEVICES= VLLM_PLUGINS= \
python3 /workspace/vllm-plugin-FL/benchmarks/benchmark_throughput_serve.py \
  --model /workspace/MiniCPM5-2B \
  --served-model-name minicpm \
  --port 9031 \
  --test-cases '[[4096,1024,64,256],[16384,1024,64,128]]'
```

4. B1 使用 `vllm-plugin-FL@47882ba2585dafdec92f06aff8ceb8af1de54630` 两次执行完整 Level 3。吞吐首组按上面的官方命令覆盖双场景；重新启动同参服务后，第二组使用未改 wrapper 分别选择单场景诊断复测，各跑四轮。这两条诊断命令不等同于再次执行完整双场景命令，不作为正式评分结果。

```bash
cd /workspace
CUDA_VISIBLE_DEVICES= VLLM_PLUGINS= \
python3 /workspace/vllm-plugin-FL/benchmarks/benchmark_throughput_serve.py \
  --model /workspace/MiniCPM5-2B --served-model-name minicpm --port 9031 \
  --test-cases '[[4096,1024,64,256]]'

CUDA_VISIBLE_DEVICES= VLLM_PLUGINS= \
python3 /workspace/vllm-plugin-FL/benchmarks/benchmark_throughput_serve.py \
  --model /workspace/MiniCPM5-2B --served-model-name minicpm --port 9031 \
  --test-cases '[[16384,1024,64,128]]'
```

两次诊断仍保持每个场景原有的长度、并发和请求数，改变的只是本次启动选择的场景集合。每个客户端任务前后读取 cgroup v1 的 OOM 状态；所有轮次请求成功，`oom_kill` 未增加。官方 A0 未公布的逐轮与运行时字段不得由租赁实验代填。

```bash
cat /sys/fs/cgroup/memory/memory.oom_control
```

## 4. 实际结果说明了什么

[实验结论] B1 的首次 Level 3 为 105/105 请求成功、102/105 答对、report score `0.9714`；第二次为 105/105 请求成功、101/105 答对、report score `0.9619`（显示为 96.2%）。两次都高于 0.95 门槛，但它们是两次独立结果，不合并求平均，也不声称精度提升。两次运行均未增加 `oom_kill`，第二次结束时 `under_oom=0`，说明客户端隔离继续有效，且未见 M1 导致精度越过验收线。这些结果仍是租赁 C500 的预验证，不是官方精度验收；组委会公布的 A0 性能基线不应被附会为本轮租赁环境的精度结果。

[实验结论] 首组是完整双场景官方命令，第二组是分别选择 4K 与 16K 的诊断复测；两组都由未改 wrapper 执行，保持 `RUNS=4`、`SKIP_FIRST=1` 和各场景原有请求参数，两个场景各八轮均全部成功。下表把每组首轮保留为原始值，各组后三轮合计六个有效轮用于描述重复性；标准差与 CV 只针对这六轮 total tok/s。六轮汇总不是官方单组评分，也不能把诊断复测说成第二次完整官方双场景运行；A0 未公布字段仍记为“—”。

B1 的 4K 六个有效轮吞吐 4967.22 tok/s，比官方 A0 的 5089.645 tok/s 低 2.41%，CV 为 4.83%；它没有稳定涨点。

16K 首组完整双场景运行的后三轮均值为 7451.75 tok/s，第二组单场景诊断复测为 7464.52 tok/s。两组在不同服务进程启动后取得，源码提交和关键文件一致；每轮均为 128/128 请求成功、输入 2,097,152 token、输出 131,072 token，且未增加 OOM。六个有效轮范围为 7450.31～7466.56 tok/s，合并描述性均值为 7458.14 tok/s、样本标准差 7.15、CV 0.096%；每组自身 CV 分别为 0.019% 和 0.025%，最低一轮也高于 7099.97 tok/s 的预设涨点门槛。因此，在这台租赁 C500、该源码和测试条件下，16K 约 7.45k tok/s 的收益是可重复的真实观测，不是挑出单轮峰值；描述性均值相对官方 A0 的 7029.675 tok/s 高约 6.10%。

两个场景六轮汇总的 Mean TTFT 分别为 2690.97 ms 和 24518.04 ms，均低于对应保守上限 3231.43 ms 和 27469.11 ms。但第二组不是完整双场景命令，且租赁环境未获正式认可，因此不能宣称官方 C500 或 BI-V150 已验收，阶段状态仍为部分验证。
