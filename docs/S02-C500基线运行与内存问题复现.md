`FlashAttentionMetadata` 增加一个可选字段，保存当前调度步的 Prefill 累计长度：

```python
    causal: bool = True
    prefill_cu_seq_lens: torch.Tensor | None = None
```

该字段默认是 `None`，因此不满足复用条件的路径仍可沿用原有计算方式。它保存的是 GPU tensor，供同一步的各层 Attention 使用。

`FlashAttentionMetadataBuilder.build` 在满足条件时只计算一次前缀和，并放入 metadata：

```python
prefill_cu_seq_lens = None
if num_prefills > 0 and not use_cascade and self.dcp_world_size == 1:
    prefill_cu_seq_lens = torch.cat(
        (prefill_seq_lens.new_zeros(1), prefill_seq_lens)
    ).cumsum(dim=0, dtype=torch.int32)
```

这里的输入是当前调度步的 `prefill_seq_lens`，输出是以 0 开头的累计长度。builder 在创建 `FlashAttentionMetadata` 时实际传入 `prefill_cu_seq_lens=prefill_cu_seq_lens`；只在非 cascade、单 DCP 分组且存在 Prefill 时创建 tensor，其他路径保持 `None`，同一步各层读取同一个结果。

`FlashAttentionImpl.forward` 优先复用 metadata 中的结果；没有预计算结果时保留原有 fallback：

```python
                num_decode_tokens = attn_metadata.num_decode_tokens
                if attn_metadata.num_prefills > 0:
                    cu_prefix_kv_lens = attn_metadata.prefill_cu_seq_lens
                    if cu_prefix_kv_lens is None:
                        cu_prefix_kv_lens = torch.tensor(
                            [0] + attn_metadata.prefill_seq_lens.tolist(),
                            device=attn_metadata.prefill_seq_lens.device,
                            dtype=torch.int32,
                        ).cumsum(dim=0, dtype=torch.int32)
                    output[num_decode_tokens:num_actual_tokens] = (
                        flash_attn_varlen_func(
                            q=query[num_decode_tokens:num_actual_tokens],
                            k=key_cache,
                            v=value_cache,
                            block_table=attn_metadata.prefill_block_table,
                            cu_seqlens_q=attn_metadata.prefill_query_start_loc,
                            cu_seqlens_k=cu_prefix_kv_lens,
                            max_seqlen_q=attn_metadata.max_query_len,
                            max_seqlen_k=attn_metadata.prefill_max_seq_len,
                            softmax_scale=self.scale,
                            causal=attn_metadata.causal,
                            window_size=self.sliding_window,
                            alibi_slopes=self.alibi_slopes,
                            softcap=self.logits_soft_cap,
                            s_aux=self.sinks,
                        )
                    )
```

修改前，`FlashAttentionImpl.forward` 每层都把 GPU 上的 `prefill_seq_lens` 转成 Python 列表，再创建张量并求 cumulative sum；`.tolist()` 会引入设备到主机的同步，42 层重复支付这笔开销。修改后，metadata builder 在当前调度步仅计算一次 `[0, len_1, …]` 的前缀和，所有层读取同一个 GPU tensor；cascade、DCP 等路径仍使用原实现。短请求的定向 Profile 中，Device→Pageable 拷贝由 42 次降为 0 次、`aten::cumsum` 由 42 次降为 1 次，证明 M1 命中预期路径；这只是机制检查，不能单独当作 16K 端到端收益。

第二处改动在 FlagGems 的 `sort.py`：先前 C500 的 4K Decode 定向 Profile 将完整排序的 Self CUDA 记为 17.49%、原直方图记为 7.43%；这说明排序值得优先检查，但含 graph replay 的 Profile 百分比不能直接当成端到端 Amdahl 占比。原实现逐个桶与每个元素比较，产生较大的桶×元素临时矩阵。新 kernel 对 MetaX 的 FP32、4-bit radix pass、长度至少 1024 的输入按 tile 直接计数；尾部无效 lane 写入额外的第 16 桶，最终只提交真实 0～15 桶。下游前缀和、稳定排序 sweep、top-p 与随机采样逻辑完全沿用原实现；其他设备、dtype 和短长度仍走原 kernel。

```python
@triton.jit
def compute_global_hist_kernel_metax_fp32_k4(
    arr_ptr, out_ptr, num_passes, m, n, tiles_n_per_cta,
    TILE_N: tl.constexpr, TILE_R: tl.constexpr,
    num_bits_per_pass: tl.constexpr, descending: tl.constexpr,
):
    tl.static_assert(num_bits_per_pass == 4)
    pid = tl.program_id(0)
    pid_n = pid // m
    pid_m = pid % m
    r: tl.constexpr = 16
    histogram_bins: tl.constexpr = 32
    bfe_mask: tl.constexpr = r - 1
    CTA_TILE_N: tl.constexpr = TILE_N * tiles_n_per_cta
    cta_n_start = CTA_TILE_N * pid_n
    cta_n_end = tl.minimum(cta_n_start + CTA_TILE_N, n)
    bin_indices = tl.arange(0, histogram_bins)

    for p in range(0, num_passes):
        bit_offset = p * num_bits_per_pass
        acc = tl.zeros((histogram_bins,), dtype=tl.int32)
        for n_start in range(cta_n_start, cta_n_end, TILE_N):
            n_offsets = n_start + tl.arange(0, TILE_N)
            mask = n_offsets < cta_n_end
            arr = tl.load(arr_ptr + pid_m * n + n_offsets, mask=mask, other=0.0)
            arr = convert_to_uint_preverse_order(arr, descending)
            key = ((arr >> bit_offset) & bfe_mask).to(tl.int32)
            key = tl.where(mask, key, r)
            acc += tl.histogram(key, histogram_bins).to(tl.int32)
        tl.atomic_add(
            out_ptr + pid_m * num_passes * r + p * r + bin_indices,
            acc, mask=bin_indices < r, sem="relaxed",
        )

def _select_global_hist_kernel(dtype, k_bits, n):
    if (
        runtime_device.vendor_name == "metax"
        and dtype == torch.float32
        and k_bits == 4
        and n >= GLOBAL_HISTOGRAM_MIN_N
    ):
        return compute_global_hist_kernel_metax_fp32_k4
    return compute_global_hist_kernel
```

`radix_sort` 中的实际调用保留原 grid 与全部后续排序步骤：

```python
global_hist_kernel = _select_global_hist_kernel(dtype, k_bits, n)
global_hist_kernel[grid_for_global_hist](
    arr, global_hist, n_passes, m, n, tiles_n_per_cta,
    TILE_N, TILE_R, k_bits, descending,
)
```

选择条件没有根据模型名、4K/16K 场景或 top-p 值写死分支。C500 上直方图和完整排序的原版→候选→恢复原版微基准均显示耗时下降；端到端结果及完整 Level 3 精度见下文。

## 2. 为什么 64GB C500 仍会出现 OOM

[实验结论] 此前租赁环境的诊断实验启动参数与后来成功运行保持一致，但当 EvalScope 客户端也可见 GPU 时，cgroup 的 `oom_kill` 计数从 1 增到 2，EngineCore 退出，后续请求只能得到连接失败。该失败发生在宿主/cgroup 内存边界，不是组委会公布的官方基线结果，也不是 C500 的 65,536 MiB 设备显存不符合赛题或模型精度失败。

[分析假设] 根因模型是：GPU 可见的客户端会加载平台插件与相关运行时，与已占用大量宿主内存的 API Server/EngineCore 叠加后超过 64 GiB cgroup 上限。不应为规避这个问题而改小 `--gpu-memory-utilization`、缩短 workload 或改动服务命令；只需要让不执行模型计算的客户端不可见 GPU，服务仍保持 GPU 可见且 `VLLM_PLUGINS=fl`。

EvalScope 是通过 `http://127.0.0.1:9031` 调用 OpenAI 兼容 API 的客户端，它不需要直接使用 C500。benchmark wrapper 的子进程会导入 vLLM CLI，因此除了把客户端 `CUDA_VISIBLE_DEVICES` 设为空，还要仅对该客户端命令把 `VLLM_PLUGINS` 设为空，避免客户端激活 FL 平台插件。这两个都是 shell 行内变量，不会改变另一个 shell 中的服务环境。

[实验结论] 阶段收口时，持久 FlagGems 分支已快进到新内核提交，启动入口在服务启动前把持久插件与 FlagGems 源码加入 Python 导入路径。单服务重启后，EngineCore 的实际 FlagGems 路径与预期一致，单个 top-p 请求正常完成且 OOM 计数不增加。一次额外的独立 Python 探针与服务并发时触发了宿主 OOM，已作为无效诊断排除；它不是新 kernel、正式 benchmark 或模型精度的失败，也不应在已占用大量内存的服务旁重复启动同类探针。
