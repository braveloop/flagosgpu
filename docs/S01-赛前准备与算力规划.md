[官方规则] 正式目标是在天数 BI-V150 和沐曦 C500 64GB 上提升 MiniCPM5-2B 的 `total tokens/s`，同时保持 MATH-500 Level 3 精度不低于 0.95，并守住 TTFT 限制。允许有实际开发量的显存管理、动态批处理、算子融合、内核重写和自研量化；禁止改变正式 `vllm serve` 参数、修改 benchmark、用超参数开启现成量化或投机采样、只切换现成算子后端、删除主要选择逻辑，或直接合并新分支获取收益。报告中的策略必须真实出现在最终代码中。

[源码事实] 本地冻结版本是 `vllm-plugin-FL@13eb9be69ecc5b5ca4f79c44e9ee40081eaa1bf0`、`FlagGems@a7620cc191a0b42e040194622c5758b22a7a25dc` 和只读参考 `vllm@ee0da84ab9e04ac7610e28580af62c365e898389`。它们只是赛前静态参照；正式实验还要在两个官方环境记录实际 import 路径、安装版本和 HEAD，不能默认容器与本机一致。

[源码事实] [MiniCPM5-2B 配置](https://modelscope.cn/models/OpenBMB/MiniCPM5-2B/resolve/master/config.json)使用 BF16、42 层、hidden size 2048、intermediate size 6144、16 个 Query Head、2 个 KV Head、head dim 128 和 131072 上下文；其 `architectures` 是 `LlamaForCausalLM`，`model_type` 是 `llama`。原始响应已按 2026-09-30 访问日期归档为 `official-materials/snapshots/minicpm5-2b-config-20260930.json`。GQA（多个查询头共享较少的键值头）比例是 8:1。每个 token 的理论 KV Cache 为：

```text
42 层 × 2（K/V）× 2 KV heads × 128 维 × 2 bytes（BF16）
= 43,008 bytes ≈ 42 KiB/token

43,008 bytes/token × 17,408 tokens/request × 64 requests
= 47,915,728,896 bytes ≈ 44.6 GiB
```

[分析假设] 这里把 16K 输入与 1K 输出按 `17,408` token/request 估算，GiB 使用 `1024^3` 换算。44.6 GiB 只含 KV Cache，不含约 5GB 权重、激活、工作区、图缓冲、运行时与 allocator reserve，因此长上下文的分页布局、临时张量和调度节奏可能决定是否 OOM；该数值不是平台实测峰值。[官方规则] [EvalScope 的 MATH-500 说明](https://evalscope.readthedocs.io/zh-cn/v1.5.1/benchmarks/math_500.html)列出 Level 3 有 105 题，约 0.962 相当于 101/105，而过线至少需要 100/105，所以相对基线大致只容许再错一道题，量化必须后置。

### 一次请求怎样走到两种芯片

[源码事实] 模型配置声明决定这里不能沿用旧版 MiniCPM 专用类。只读参考 `vllm/vllm/model_executor/models/registry.py:152@ee0da84` 把 `LlamaForCausalLM` 注册到 `llama.py:LlamaForCausalLM`，后者进入 `LlamaModel`，再创建 42 个 `LlamaDecoderLayer`。每层先以 `input_layernorm` 处理残差并进入 `LlamaAttention` 的 `qkv_proj → rotary_emb → Attention → o_proj`，再经 `post_attention_layernorm`、`LlamaMLP` 的 `gate_up_proj → SiluAndMul → down_proj`；42 层之后还有 final `RMSNorm`，随后由 `lm_head` 和 `LogitsProcessor` 产生 logits，采样与流式响应由模型类外的引擎链继续完成。

```text
OpenAI API 请求
  → vLLM scheduler / vllm_fl.worker.model_runner
  → registry.py:LlamaForCausalLM → LlamaModel
  → 42 × LlamaDecoderLayer
      → input RMSNorm → QKV GEMM → RoPE
      → Attention.forward
          → 必要时 unified_kv_cache_update
          → unified_attention_with_output
      → O-Proj → 残差
      → post-attention RMSNorm → Gate/Up GEMM → SiLU×gate → Down-Proj
  → final RMSNorm → lm_head / LogitsProcessor → logits
  → 引擎采样、流式返回与下一轮 Decode
```

[源码事实] 这条图的输入是已经分词和调度后的 token，模型类输出下一 token 的 logits；响应状态和采样不属于 `LlamaForCausalLM` 本身。`vllm/vllm/model_executor/layers/attention/attention.py@ee0da84` 中，`Attention.forward` 根据 backend 的 `forward_includes_kv_cache_update` 决定是否先调用 `unified_kv_cache_update`，再由 `unified_attention_with_output` 调用平台实现。分页 KV Cache 的 slot mapping 和 Attention metadata 来自 model runner；因此改 backend 声明、metadata 或 cache write 都会跨层影响正确性。[待平台验证] 官方容器实际解析到的类、import 路径和补丁集必须由环境探针与 server log 确认，不能仅凭本地只读仓库认定；只有确认命中目标 `AttentionFLBackend` 时才执行 C0。

[源码事实] BI-V150 的本地固定 dispatch 配置 `vllm-plugin-FL/vllm_fl/dispatch/config/iluvatar.yaml@13eb9be` 会优先调用 FlagGems selector，但 selector 在未显式启用 `VLLM_FL_USE_FLAGGEMS_ATTN` 时返回 `TRITON_ATTN` 枚举路径，而不是自动返回 `AttentionFLBackend`。官方镜像还可能有不同的环境变量、注册覆盖或补丁，因此真实 Attention backend 只能由未改正式服务参数的启动日志、环境白名单和 trace 确认。只有确实命中 `AttentionFLBackend/AttentionFLImpl → FlagGems flash_api/flash_kernel` 时，C0 与 I1～I5 才适用；不得为了让候选生效而擅自切换后端。若未命中，C0 以“不适用”闭环，并在阶段 2 对实际 backend 重新归因。

[源码事实] C500 在 `vllm-plugin-FL/vllm_fl/dispatch/config/metax.yaml@13eb9be` 中只为 Attention 选择 `vendor:metax`，进入 `vllm-plugin-FL/vllm_fl/dispatch/backends/vendor/metax/impl/attention/flash_attn.py` 的 `FlashAttentionMetadataBuilder` 与 `FlashAttentionImpl`；RMSNorm、SiLU 和 RoPE 仍优先 FlagGems，不应把同目录下可见的 MACA wrapper 当作当前默认路径。[待平台验证] C500 的真实注册结果和动态库实现必须从启动日志、import 路径与 trace 确认。

[源码事实] `vllm-plugin-FL/vllm_fl/worker/scheduler_fl.py` 的 `AsyncSchedulerFL` 不是正常链的必经节点。`vllm-plugin-FL/vllm_fl/worker/worker.py:WorkerFL.__init__` 只有在 `num_speculative_tokens == 1` 且 `async_scheduling` 开启时才改用它，而正式参数未启用投机采样；后续 G1 应先追踪实际 scheduler。[分析假设] MetaX 的 FlagTree 公开材料若只说明 C550，也不能直接当作 C500 的编译或调优结论，必须使用与官方 C500 镜像相匹配的版本资料。

### 先确定结论与证据边界

[分析假设] 建议采用“本机静态开发 → 市场 C500 同芯片诊断与预验证 → 官方认可环境阶段出口”的三级路线。本机仍只做源码阅读、编辑、文档、Git 和静态检查；本文不修改项目现有的“本机不运行”边界。市场 C500 16GB/32GB 主要回答编译、分支、算子结果与目标计数器问题，市场 C500 64GB 可提前暴露真实长上下文和大并发问题；但只有组委会分配或书面认可且驱动、容器、源码与设备身份匹配的实例，结果才可作为正式 C500 证据。

### 用显存账本决定每种实例做什么

KV Cache 是推理时为每个历史 token 保存 Key 和 Value 的显存区域。MiniCPM5-2B 保持 BF16、42 层、2 个 KV Head、每个 Head 128 维；每个 token 的理论 KV 占用为 `42 × 2(K/V) × 2 heads × 128 × 2 bytes = 43,008 bytes`。下表使用二进制 `GiB=1024^3 bytes`，16K 输入按 16,384 token、1K 输出按 1,024 token 计算。

| 输入/输出 | 并发请求数 | 仅 KV Cache 估算 |
|---|---:|---:|
| 4K + 1K | 64 | 13.125 GiB |
| 16K + 1K | 1 | 0.6973 GiB |
| 16K + 1K | 8 | 5.5781 GiB |
| 16K + 1K | 16 | 11.1563 GiB |
| 16K + 1K | 32 | 22.3125 GiB |
| 16K + 1K | 64 | 44.625 GiB |

[分析假设] 这些都是容量估算，不是实测峰值，且均未计入约 5GB BF16 权重、激活、Attention workspace、图缓冲、编译缓存、运行时和 allocator reserve。由此不能承诺“KV 数字低于显存就一定能跑”：例如 4K+1K、并发 64 的 KV 约 13.125 GiB，叠加其他占用后可能挤入 32GB，也可能因实现和预留策略失败；16K+1K、并发 64 仅 KV 已达 44.625 GiB，必须最终在官方认可的 64GB 环境观察真实 token budget、分页分配和 OOM 边界。

分工据此固定如下，避免为了塞进便宜卡而改变待验证路径。

1. **C500 16GB：同芯片早期诊断。** 适合 compiler/import 检查、单算子真实长 KV shape、差分测试、短请求和小并发 smoke，也适合确认 `.tolist()` 同步或临时分配是否按设计消失。它不承担正式并发、吞吐、TTFT、完整精度或 graph 结论。

2. **C500 32GB：整模桥接。** 适合把已经通过单算子门槛的候选接入完整模型、扩大 batch、运行短长混合 smoke，并尝试 4K 场景的诊断版本。能否容纳 4K 正式 workload 必须实测，本文不作承诺；即使能跑，也不把结果当官方认可 C500 64GB 的性能证据。

3. **市场 C500 64GB：高显存预验证。** 用于提前检查真实 16K、并发 64、scheduler、graph capture/replay、峰值显存、TTFT、吞吐和完整 Level 3。它只在候选已通过便宜卡诊断或必须直接观察真实内存/调度时使用；除非组委会书面认可并确认环境指纹匹配，否则这些结果仍是预验证证据，正式出口必须在组委会分配环境重跑。

4. **MR-V100/待确认的天垓 150：Iluvatar 预检。** MR-V100 只提供工具链与接口证据；天垓 150 只有在确认具体设备就是所需 BI-V150、逻辑显存与官方镜像一致后，才可能提升证据等级。阶段 4、阶段 7 和所有 BI-V150 性能出口仍以官方 BI-V150 为准。

整个分层过程必须保留模型的 42 层、16 个 Query Head、2 个 KV Head、head dimension 128 和 BF16 数据类型。本成本策略不使用量化、CPU/NVMe offload、减少层数或缩短正式 workload 来“适配”小卡，因为那会改变显存、kernel、数据传输和调度路径；诊断可以缩小 batch 或请求数，但必须明确标为诊断证据。

### 七阶段怎样分配卡型与触发升卡

便宜卡是否值得租，不由“能开机”决定，而由它能否在进入正式卡前淘汰错误候选决定。下表与[七阶段详细优化方案](../DETAILED_OPTIMIZATION_PLAN.md)逐项对应；“正式出口”表示只有该列证据齐全，阶段才可按原计划验收。

| 阶段 | 本机与便宜卡工作 | 必须使用的正式出口 | 升卡或停止触发 |
|---:|---|---|---|
| 1｜规则、环境、基线 | 本机冻结规则与源码；首次用市场 C500 16GB 核对设备、镜像、编译和短请求，若整模装不下再用 32GB 桥接，64GB 只作高显存预验证 | 组委会分配或书面认可且环境匹配的 C500 64GB 与官方 BI-V150：环境指纹、短长请求、完整 Level 3、4K/16K 重复基线 | 市场卡后端/镜像不同则停止外推；真实正式波动、TTFT 或适用时的 C0 调查直接上官方平台 |
| 2｜Profile 归因 | 市场 C500 16GB 观察单层同步、分配和 kernel 命中；32GB/64GB 观察整模与长上下文预验证。MR-V100 只预检 Iluvatar profiler/编译工具是否可用 | 官方认可 C500 64GB 与 BI-V150 分别采集 4K/16K、Prefill、混合、Decode、收尾的完整 trace | 需要正式并发、真实 KV 水位、scheduler、graph、带宽或稳定耗时时升官方平台；市场卡耗时占比不参与正式候选排名结论 |
| 3｜低风险开销清理 | 市场 C500 做 M1 与 C500 侧 R1 的编译、差分和目标计数器检查；MR-V100 只预检 I3/R1 的 Iluvatar 编译与接口 | 对应官方认可 C500 64GB/BI-V150 的 token、Level 3、4K/16K、TTFT 与端到端 A0/B/A1 | 差分通过且目标计数器变化后升对应平台；输出错误、目标计数器不变或同一问题三次失败则退出候选 |
| 4｜BI Attention/KV | 本机静态开发；MR-V100 可做 FlagTree Iluvatar 编译与通用接口预检，但不调 BI 性能参数 | 官方 BI-V150 先按实际 backend 完成 Attention/KV、4K/16K 与 shadow shapes；仅目标 FlagGems 实现命中时执行计划的 GQA Decode、Prefill 和 KV write 候选 | 涉及 tile/warp/stage、occupancy、带宽、Paged KV 或真实 graph 时直接用 BI-V150；MR-V100 数字不得用于升降候选 |
| 5｜C500 与共享算子 | 市场 C500 做 MACA 准备路径、RoPE/Norm/SiLU 单算子差分和整模预验证 | 官方认可 C500 64GB 完成 MACA、metadata、4K/16K 与 graph 边界；共享算子在 BI-V150 回归 | 需要正式图覆盖、峰值内存或约 1% 端到端判定时转到官方平台 |
| 6｜调度、图、可选量化 | 市场卡只做通用调度状态机和 fallback 预验证；不得用量化/offload 让候选适配小卡 | 取得书面规则许可后，在官方认可 C500 64GB 与 BI-V150 验证通用 shape-aware 调度、graph 和任何可选 W8A16 | 进入正式 TTFT、16K KV 压力或数值路径时直接转到官方平台；无书面许可则不启动量化 |
| 7｜组合回归与报告 | 本机整理 commit、manifest、消融与报告；租赁卡只可预复查，不生成最终成绩 | 官方认可 C500 64GB 与官方 BI-V150 各自完成冷启动、两场景、完整精度、至少两轮独立复现和第二 checkout | 本阶段不允许普通市场实例替代；任何组合错误回退到最后一个已知正确组合，再预约官方平台复验 |

跨阶段还使用五个统一触发器：小卡 OOM 且候选本身已通过较小 shape；小卡与官方镜像、后端或虚拟化方式不一致；问题涉及真实并发、KV 水位、allocator、scheduler、graph、带宽或 TTFT；候选已通过差分并准备进入端到端验收；继续使用小卡的预计总成本已高于直接租市场 64GB 预验证。便宜卡上更快或更慢都只形成诊断线索，不能形成平台性能结论。

### 预算怎样计算并控制每次租赁

单纯市场时租成本可写成 `C = Σ(实例小时数 h_i × 单价 p_i)`。若全部 140 小时都租市场 C500 64GB，示例成本是 `140 × ¥4 = ¥560`；若拆为 `70h C500 16GB + 20h C500 32GB + 50h C500 64GB 高显存预验证`，成本为 `70×1.5 + 20×2.5 + 50×4 = ¥355`，节省 `¥205`，即约 `36.6%`。组委会分配平台的卡时不按截图单价计入这个公式，其用途和证据等级也不能与市场租赁混为一谈。

这个数字只是展示计算方法，不是已批准预算，也不含官方 BI-V150/C500 卡时、数据盘、镜像、网络、停机仍计费、失败重跑或价格变化。市场便宜卡若使同一工作耗时变长，C500 16GB 相对市场 64GB 的纯时租盈亏点是 `4/1.5≈2.67` 倍，C500 32GB 是 `4/2.5=1.6` 倍；超过该倍率，仅比较实例费已经不省钱，还未计入人工等待和迁移成本。

每次租赁按以下流程控制，不把“先开机看看”变成无边界消费。

1. **租前 checklist。** 重新截图价格与库存，确认计费粒度、关机/释放规则、系统盘和数据盘、镜像与驱动、实际芯片/显存、虚拟化或共享方式、模型和依赖能否合法迁入，以及是否支持快照或持久卷。为本次租赁写下单一候选、预计小时数、产出文件和退出条件；未获得用户明确授权前不下单。

2. **首次 1～2 小时预检。** 前 30 分钟保存设备、vcore/vmemory、CPU/RAM、驱动、运行时、编译器、容器和挂载指纹；随后验证后端选择与最小 kernel 编译，再做一个小 shape 差分和一个短请求 smoke。两小时内仍不能确认环境相容性，就停止计费并先处理镜像或平台问题，不加载完整正式实验队列。

3. **单候选退出。** 一次只验证一个假设；编译和差分通过后才进入整模，整模行为通过后才预约正式卡。若输出错误、目标同步/分配未改变、fallback 不可达或便宜卡环境与官方路径不一致，就记录证据并结束该候选，而不是用更多小时盲调。

4. **三次失败停止。** “一次尝试”必须包含明确假设、一个受控改动和可检查结果；同一问题三次仍未解决时停止第四次试错，按项目失败账本记录三次证据，重新查 FlagOS、KernelGen 和芯片官方资料。只有出现新的权威线索后才重新租卡。

5. **备份后释放。** 结束前把源码 commit/patch、环境 manifest、命令、stdout/stderr、差分结果、原始 CSV、trace 和结论复制到持久存储，并在本地或团队仓库校验文件数量与 hash。FlagOS [线上实验室使用指南](https://docs.flagos.io/projects/onlinelaboratory/zh-cn/latest/onlinelaboratory.html)明确警告环境释放后数据将永久删除且无法恢复；算力市场实例是否同样处理必须另行确认，但统一采用“先验证备份，再释放并停止计费”的保守流程。

#### C500 租赁实例的持久工作区

[官方资料] [AI 算力平台容器文档](https://ai.gitee.com/docs/compute/container)保证 `/data` 与 `/root` 在重启、更换镜像和重置后持久；销毁实例会删除全部数据，因此 `/data` 仍不能替代租期结束前的本地或仓库备份。C500 辅助脚本 `scripts/c500_persistent_workspace.sh` 只提供 `check`、`prepare` 和 `serve` 三个显式模式，不安装依赖、不设置开机自启。完成中的 benchmark 和 server 停止后，才可在有足够内存余量时把模型与数据集复制到 `/data/flagos/models/MiniCPM5-2B` 和 `/data/flagos/datasets/math_500`。

```bash
# 只读检查：包括固定起点与当前分支的祖先关系、模型/数据集、MACA 环境与 import 路径
bash /data/flagos/scripts/c500_persistent_workspace.sh check

# 仅在 /workspace 目标缺失且 /data 内容验证通过时创建符号链接；不替换现有目录
bash /data/flagos/scripts/c500_persistent_workspace.sh prepare

# check 通过且没有其他 vllm serve 进程时，以官方 C500 参数前台启动
bash /data/flagos/scripts/c500_persistent_workspace.sh serve
```

`check` 要求固定比赛 commit 是当前开发 HEAD 的祖先，同时仍要求指定分支和干净工作树，并输出实际 HEAD。它会如实显示 `/opt/conda` 等实际 import 来源；只有源码保存在 `/data` 不等于当前安装包已从该开发源码导入。`/workspace` 未绑定 `/data` 的告警只描述路径关系，不证明两处内容相同，也不证明运行时已使用开发代码。`prepare` 不复制数据，也不删除、重命名或覆盖已有 `/workspace` 路径；遇到已有目录时必须先停止相关进程并人工核对，不得用脚本强制替换。

### 最终决策、待确认项与采用条件

当前建议不是“尽量不用 64GB”，而是“把普通市场 64GB 用于高风险预验证，把正式证据留给官方认可环境”。C500 16GB 的首选价值是尽早发现编译、接口、差分和同步问题；32GB 在需要完整模型与更大 batch 时补位；市场 64GB 提前验证真实 4K/16K、调度、graph 和显存压力。最终 TTFT、吞吐、完整精度和干净复现必须回到组委会分配或书面认可且环境匹配的 C500 64GB；MR-V100 或待确认的天垓 150 也不能替代 BI-V150 阶段出口。

首次租赁已经提供 C500 64GB、64 GiB 宿主/cgroup 内存和 MACA 运行时线索，但在把市场实例结果外推到正式环境前，仍需取得下列事实；任何一项未知都要在实验记录中保持 `[待平台验证]`：

- C500 16GB/32GB/64GB 分别是物理卡、VF、sGPU 还是其他切分，实际 vcore/vmemory、共享和超售策略是什么。

- 三种 C500 商品是否提供与正式比赛相同或足够接近的 MACA 驱动、编译器、容器镜像和 `vllm-plugin-FL` 路径。

- “天垓 150”商品的精确芯片 PCI/逻辑设备名称是否为 BI-V150、为何只显示 32GB，以及是否能使用比赛指定镜像。

- 数据盘在关机、到期和释放后的保留时间，备份出口、流量费、镜像费和失败工单是否计费。
