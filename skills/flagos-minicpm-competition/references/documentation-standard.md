# FlagOS MiniCPM5-2B 优化文档规范

本规范用于把比赛中的分析、修改、失败与验证沉淀成完赛后仍可循序学习的中文资料。读者不需要预先理解 vLLM、Triton、Attention 或两种竞赛加速卡；文档应从问题现象讲到运行路径，再把源码、实验和结论连成一条可复核的证据链。它约束的是解释质量和实验可信度，不要求为了篇幅填充内容，也不允许用计划中的结果冒充已经完成的验证。

## 1. 面向读者和七阶段生命周期

`docs/` 中的主要文档默认面向零背景读者。一个术语首次出现时，应先用普通中文解释它是什么、为何存在，再指出它在 MiniCPM5-2B 推理链路中的位置和相邻环节；随后给出真实源码符号、文件路径和适用提交。像 GQA、Prefill、Decode、Paged KV Cache、TTFT、TPOT、graph replay 这类词不能只给英文缩写，也不能脱离当前执行路径孤立定义。

文档生命周期严格跟随 `DETAILED_OPTIMIZATION_PLAN.md` 的七个阶段：规则与基线、Profile 归因、低风险开销清理、BI-V150 主线、C500 与共享算子、调度/图执行/可选量化、组合回归与报告。前一阶段未通过出口时，后一阶段只能记录准备事项，不能写成已完成结论。只有已经完成、能够复现、有实质交付，并且完成其声明范围内必要验证的阶段成果，才建立一份独立复现文档。完整基线成果至少要把环境身份、完整 MATH-500 Level 3、4K/1K 与 16K/1K 重复基线、原始证据和边界结论连成闭环；优化成果至少要完成实现、正确性与 fallback、完整 Level 3、两个吞吐场景，并据此作出保留或回滚决定。单独打通环境、闭环一个根因、形成待验证补丁、执行一条命令或一轮实验，以及结论仍是“继续验证”，都不满足新建文档门槛，只记录在当前阶段材料与不可变证据目录中。同一合格成果的多轮实验与失败证据合并到同一文档，后续补证据时继续更新该文档，不重复新建；没有合格成果时不得创建占位文档。

每份阶段文档开头使用下列状态之一，并在证据变化后及时更新。状态描述的是整份文档的成熟度，正文中的单项结论仍需单独标注证据状态。

| 文档状态 | 含义 |
|---|---|
| `草拟中` | 正在建立问题模型，材料尚不完整 |
| `待平台验证` | 本地静态分析或实现已完成，缺少官方平台结果 |
| `部分验证` | 仅部分平台、场景或验收项已有结果 |
| `已验收` | 该阶段出口所需证据齐全且可复核 |
| `已归档` | 完赛后冻结，仅修正明确错误或补充索引 |

## 2. 文档结构和叙述密度

已完成小阶段的复现文档应先写一段约 150–300 个中文字符的白话引言，说明机制做什么、解决哪一个比赛问题、为何值得研究，以及正文将沿哪条源码和实验路径展开。正文通常组织为 4–6 个有实际问题意识的主章节，例如背景与边界、源码路径、复现步骤、实验结果、恢复与后续。章节数服务于内容，不为短小勘误或索引强行套模板，也不要把每个条件拆成一个浅标题。

普通解释段落围绕一个问题或机制写 3–6 个相互衔接的句子，依次交代前提、动作或状态变化、结果和失败边界。避免连续出现只有一句话的碎片段落，也不要通过删掉所有空行把无关内容粘成文字墙。连续叙述在责任主体、数据流阶段或失败模式发生变化时自然分段，路径和符号应嵌入解释它们为何重要的段落中，而不是单独悬挂成“源码位置”。

实施过程使用编号步骤，但不把步骤写成密集清单。每一步保持 1–3 个完整句子，说明这一步改变什么、为何此时做、产生什么可检查结果；步骤之间保留一个空行。并列字段、实验组合和互斥选择可以使用表格或项目列表，列表前后仍应交代它们与当前因果链的关系。

## 3. 源码、公式与证据交错

按“现象或问题 → 当前调用路径 → 核心代码 → 修改理由 → 验证证据 → 局限”的节奏组织技术内容。源码引用至少包含仓库、相对路径、符号名和固定 commit；若官方平台实际加载路径或 commit 不同，应同时记录并解释差异。文档引用的是代表性逻辑而不是无上下文的整文件转储，任何结论都必须能回到实际代码或官方资料。

代码块通常不超过 50–60 行，并在自然逻辑边界拆分。每个代码块后紧接一段 3–6 句的解释，覆盖输入、输出、布局或所有权、关键不变量、状态变化和 fallback；不可拆分的较长代码块要在块前说明原因。伪代码必须标为伪代码，建议实现必须标为建议，不能让读者误以为它已经存在于比赛分支。

公式要写清变量、单位、数据类型、统计口径和假设，并至少给出一个与当前模型或场景对应的代入结果。例如 KV Cache 估算要说明层数、K/V 份数、KV Head、head dimension、元素字节数，以及 GiB 使用二进制换算。估算值与实测峰值必须分开，前者标注未计入的权重、激活、workspace、图缓冲和 allocator reserve，后者关联原始日志或汇总文件。

采用以下正文标签区分事实成熟度，避免把推测写成结论：

| 标签 | 使用条件 |
|---|---|
| `[官方规则]` | 来自当前赛题页面或组委会书面答复 |
| `[源码事实]` | 可由指定路径、符号和 commit 直接确认 |
| `[分析假设]` | 有推理依据但尚未由实验排除其他解释 |
| `[待平台验证]` | 只能在 BI-V150 或 C500 上完成的验证尚缺失 |
| `[实验结论]` | 有完整实验身份、原始数据和验收口径支持 |
| `[已否决]` | 已由反例、回退或不合规证据排除 |

## 4. 平台和实验记录

所有性能、正确性与精度结论都要绑定不可变实验身份。实验记录至少包括日期和实验 ID、BI-V150 或 C500、硬件与显存、驱动/容器/软件版本、三个仓库的实际 commit 与 import 路径、服务参数、模型与 workload、采样参数和 seed、冷启动或 graph 状态、重复次数和统计方法。缺少这些信息的数据可以用于形成假设，但不能写成稳定收益或最终比赛成绩。

开发中的单变量实验不要求逐次建立 Git commit。已提交实验以仓库、完整 commit SHA、实际远端 import 路径和不可变实验 ID 标识；未提交实验必须记录仓库、完整 base SHA、完整归档 scoped diff 的 SHA-256、全部改动或新增文件的 SHA-256、实际远端 import 路径和不可变实验 ID，不能只写 base commit。相关代码、文档、失败修正和同步操作应累积到逻辑自洽的小阶段交付，在完成必要验证并得出“保留、继续验证或回滚”决定后再提交；用户明确要求时可以提前提交。初始化并推送根仓库的明确请求只授权当次提交，不构成持续授权；不得重写或 force-push 已推送历史（包括 `47882ba`）。不得放宽 `scripts/c500_persistent_workspace.sh` 的 clean-worktree guard；dirty 实验必须使用独立且显式的 manifest 和 activation 流程。

结果必须先按平台分开，再在平台内区分 4K/1K、16K/1K、Prefill 和 Decode。端到端表格至少报告请求成功数、total/output throughput、Mean/median/P99 TTFT、TPOT、ITL、峰值内存，以及均值、标准差或 CV；算子结果不能替代端到端结果。BI-V150 的 FlagGems Attention 证据不能外推为 C500 MACA 结论，4K 提升也不能掩盖 16K 回退。

实验集合只有达到第一节定义的实质性阶段成果门槛时，才建立一份新的复现文档；环境打通、单点根因、待验证补丁、单次命令、raw run、失败样本或“继续验证”结论只归入当前阶段材料和实验证据目录。raw CSV、summary CSV、服务日志、环境 manifest、逐题结果和 trace 仍按不可变实验 ID 单独归档，但它们不计入学习文档编号。每份复现文档都要依次写清以下步骤：

1. 先陈述要验证的单一假设、预期变化的 trace 或计数器，以及不应退化的验收项。若一次实验混入多个改动，应拆分或明确说明无法消融的原因。

2. 记录 A/B 或 A0/B/A1 的共同环境、原始命令、输入和输出文件位置。正式性能数据只来自官方平台和官方 workload，本机静态检查不得写成运行验证。

3. 展示原始数据摘要并解释波动、失败请求、异常输出与内存变化。单次峰值只能标为峰值，不能称为稳定吞吐。

4. 给出与文档范围匹配的结论，并把结论映射到代码 commit、正确性结果、MATH-500 Level 3、正式吞吐场景和规则依据。优化成果必须在完成必要验证后明确选择“保留、回滚或否决”；若只能选择“继续验证”，就继续归档实验，不新建成果文档。文档还要给出恢复或回滚步骤、未解决边界，并记录关键证据文件的 SHA-256；缺失项使用 `[待平台验证]`，不得留给读者猜测。

复现命令必须写明工作目录、环境变量的作用范围、硬件与软件身份、仓库 SHA 以及实际 import 路径，并区分预期结果和实际结果。命令和文档中不得记录密码、私钥、令牌或可复用的访问凭据。市场租赁 C500 可以支撑诊断与预验证结论，但不得由此宣称 C500 或 BI-V150 的正式阶段已验收。

## 5. 命名、维护与验收

`docs/` 中的中文学习资料采用全局唯一的 `SNN-中文主题.md` 编号，`S00-学习索引.md` 固定为索引，后续编号按文档形成顺序递增。`SNN` 只是排序和阅读标识，不等同于七阶段编号；文档在索引中另行注明所服务的阶段。队名、模型名等固有名称可保留原文，生成脚本和正式 PDF 导出件不强制使用学习文档编号。文件重命名后同步更新索引和站内相对链接，不保留指向不存在文档的链接。

每个符合第一节定义的实质性阶段成果使用一份复现文档，同一成果的补充实验、失败分析与官方平台后续验证优先回填原文档。环境打通、单点根因、待验证补丁和“继续验证”实验继续留在所属阶段材料中；不得预建占位文件，也不得把每条命令、每轮运行或每个暂时错误切成独立短文。索引在新增成果文档、路径、阅读顺序、阶段或文档状态发生实质变化时同步更新。

文档更新应与工程事实同步。代码路径、符号、commit、官方规则或实验结论变化时，修改对应段落和状态，保留必要的历史对比但明确“当前值、历史最好值、诊断失败样本”的身份。删除或回滚的优化不能继续出现在最终成果列表中；若失败本身具有学习价值，应保留原因、证据和后续边界，并标为 `[已否决]`。

完成主要文档后按以下顺序验收：

1. 检查白话引言、术语定义、章节深度和段落连贯性，确认零背景读者能沿调用路径理解问题。检查步骤是否疏密适中，代码块后是否立即解释其作用与边界。

2. 检查每个性能或正确性主张是否能回到官方资料、固定 commit、源码符号或实验文件。核对公式单位、假设和换算，确保估算与实测没有混写。

3. 检查 BI-V150/C500、4K/16K、Prefill/Decode 是否分别呈现，实验身份和状态标签是否完整。最后验证站内相对链接、`git diff --check` 和文档索引，但不运行任何项目代码或 GPU 测试。
