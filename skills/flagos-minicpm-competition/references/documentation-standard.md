# FlagOS MiniCPM5-2B 优化文档规范

本规范用于把比赛中的分析、修改、失败与验证沉淀成完赛后仍可循序学习的中文资料。读者不需要预先理解 vLLM、Triton、Attention 或两种竞赛加速卡；文档应从问题现象讲到运行路径，再把源码、实验条件、数值结果和结论连成完整的技术逻辑。它约束的是解释质量和实验可信度，不要求为了篇幅填充内容，也不允许用计划中的结果冒充已经完成的验证。

## 1. 面向读者和七阶段生命周期

`docs/` 中的主要文档默认面向零背景读者。一个术语首次出现时，应先用普通中文解释它是什么、为何存在，再指出它在 MiniCPM5-2B 推理链路中的位置和相邻环节；随后给出真实源码符号、文件路径和适用提交。像 GQA、Prefill、Decode、Paged KV Cache、TTFT、TPOT、graph replay 这类词不能只给英文缩写，也不能脱离当前执行路径孤立定义。

文档生命周期严格跟随 `DETAILED_OPTIMIZATION_PLAN.md` 的七个阶段：规则与基线、Profile 归因、低风险开销清理、BI-V150 主线、C500 与共享算子、调度/图执行/可选量化、组合回归与报告。前一阶段未通过出口时，后一阶段只能记录准备事项，不能写成已完成结论。只有已经完成、能够复现、有实质交付，并且完成其声明范围内必要验证的阶段成果，才建立一份独立复现文档。完整基线成果至少要写清环境身份、完整 MATH-500 Level 3、4K/1K 与 16K/1K 重复基线和结论；优化成果至少要完成实现、正确性与 fallback、完整 Level 3、两个吞吐场景，并据此作出保留或回滚决定。单独打通环境、闭环一个根因、形成待验证补丁、执行一条命令或一轮实验，以及结论仍是“继续验证”，都不满足新建文档门槛。同一合格成果的后续验证继续更新原文档，不重复新建；没有合格成果时不得创建占位文档。

每份阶段文档开头使用下列状态之一，并在验证状态变化后及时更新。状态描述的是整份文档的成熟度，正文中的单项结论仍需单独标注成熟度。

| 文档状态 | 含义 |
|---|---|
| `草拟中` | 正在建立问题模型，材料尚不完整 |
| `待平台验证` | 本地静态分析或实现已完成，缺少官方平台结果 |
| `部分验证` | 仅部分平台、场景或验收项已有结果 |
| `已验收` | 该阶段出口所需证据齐全且可复核 |
| `已归档` | 完赛后冻结，仅修正明确错误或补充索引 |

## 2. 文档结构和叙述密度

已完成小阶段的复现文档应先写一段约 150–300 个中文字符的白话引言，说明机制做什么、解决哪一个比赛问题、为何值得研究，以及正文将沿哪条源码和实验路径展开。正文通常组织为 4–6 个有实际问题意识的主章节，例如问题背景、源码路径、复现步骤和实验结果。章节数服务于内容，不为短小勘误或索引强行套模板，也不要把每个条件拆成一个浅标题。

普通解释段落围绕一个问题或机制写 3–6 个相互衔接的句子，依次交代前提、动作或状态变化和结果。避免连续出现只有一句话的碎片段落，也不要通过删掉所有空行把无关内容粘成文字墙。连续叙述在责任主体、数据流阶段或失败模式发生变化时自然分段，路径和符号应嵌入解释它们为何重要的段落中，而不是单独悬挂成“源码位置”。

实施过程使用编号步骤，但不把步骤写成密集清单。每一步保持 1–3 个完整句子，说明这一步改变什么、为何此时做、产生什么可检查结果；步骤之间保留一个空行。并列字段、实验组合和互斥选择可以使用表格或项目列表，列表前后仍应交代它们与当前因果链的关系。

## 3. 源码、公式与结果交错

按“现象或问题 → 当前调用路径 → 核心代码 → 修改理由 → 验证结果”的节奏组织技术内容。源码定位至少包含仓库、相对路径、符号名和固定 commit；若官方平台实际加载路径或 commit 不同，应同时记录并解释差异。文档展示的是代表性逻辑而不是无上下文的整文件转储，任何结论都必须与实际代码和已完成验证一致。

代码块通常不超过 50–60 行，并在自然逻辑边界拆分。每个代码块后紧接一段 3–6 句的解释，覆盖输入、输出、布局或所有权、关键不变量、状态变化和 fallback；不可拆分的较长代码块要在块前说明原因。伪代码必须标为伪代码，建议实现必须标为建议，不能让读者误以为它已经存在于比赛分支。

公式要写清变量、单位、数据类型、统计口径和假设，并至少给出一个与当前模型或场景对应的代入结果。例如 KV Cache 估算要说明层数、K/V 份数、KV Head、head dimension、元素字节数，以及 GiB 使用二进制换算。估算值与实测峰值必须分开，前者标注未计入的权重、激活、workspace、图缓冲和 allocator reserve，后者写明采集平台和实验条件。

采用以下正文标签区分事实成熟度，避免把推测写成结论：

| 标签 | 使用条件 |
|---|---|
| `[官方规则]` | 来自当前赛题页面或组委会书面答复 |
| `[源码事实]` | 可由指定路径、符号和 commit 直接确认 |
| `[分析假设]` | 有推理依据但尚未由实验排除其他解释 |
| `[待平台验证]` | 只能在 BI-V150 或 C500 上完成的验证尚缺失 |
| `[实验结论]` | 已完成对应实验并满足验收口径 |
| `[已否决]` | 已由反例、回退或不合规结果排除 |

## 4. 平台和实验记录

所有性能、正确性与精度结论都要说明实验身份。学习文档至少包括日期和实验 ID、BI-V150 或 C500、硬件与显存、驱动/容器/软件版本、三个仓库的实际 commit 与 import 路径、服务参数、模型与 workload、采样参数和 seed、冷启动或 graph 状态、重复次数和统计方法。缺少这些信息的数据可以用于形成假设，但不能写成稳定收益或最终比赛成绩。

开发中的单变量实验不要求逐次建立 Git commit。学习文档只写与结论对应的仓库、完整 commit、实际远端 import 路径和实验 ID；未提交实验的 diff 与文件哈希仍在内部实验清单中维护，不进入学习正文。相关代码、文档、失败修正和同步操作应累积到逻辑自洽的小阶段交付，在完成必要验证并得出“保留、继续验证或回滚”决定后再提交；用户明确要求时可以提前提交。初始化并推送根仓库的明确请求只授权当次提交，不构成持续授权；不得重写或 force-push 已推送历史（包括 `47882ba`）。不得放宽 `scripts/c500_persistent_workspace.sh` 的 clean-worktree guard；dirty 实验必须使用独立且显式的 manifest 和 activation 流程。

结果必须先按平台分开，再在平台内区分 4K/1K、16K/1K、Prefill 和 Decode。端到端表格至少报告请求成功数、total/output throughput、Mean/median/P99 TTFT、TPOT、ITL、峰值内存，以及均值、标准差或 CV；算子结果不能替代端到端结果。BI-V150 的 FlagGems Attention 证据不能外推为 C500 MACA 结论，4K 提升也不能掩盖 16K 回退。

学习正文中的性能结果只分两类：`A0` 是组委会正式公布的基线，`B1` 是当前改进。官方未公布的 A0 字段统一写“—”，不得用租赁平台或内部未改原版运行代填。每个平台的结果摘要只列 A0/B1×4K/16K 四行。为判断因果而保留的同机器“未改原版 → 单一候选 → 恢复原版复测”是内部配对控制，用于漂移拒绝，不形成第三类学习结果；历史实验 ID 保持不变，即使其中含 `A0` 字样也不重命名。

实验集合只有达到第一节定义的实质性阶段成果门槛时，才建立一份新的复现文档；环境打通、单点根因、待验证补丁、单次命令、raw run、失败样本或“继续验证”结论只归入内部实验记录。raw CSV、summary CSV、服务日志、环境 manifest、逐题结果和 trace 仍按不可变实验 ID 单独保存，但不得在学习正文中列出、链接或引用，也不计入学习文档编号。每份复现文档都要依次写清以下步骤：

1. 先陈述要验证的单一假设、预期变化的 trace 或计数器，以及不应退化的验收项。若一次实验混入多个改动，应拆分或明确说明无法消融的原因。

2. 记录 A0/B1 的来源与可比边界，并在内部用同平台、同参数、同版本和同热状态的“未改原版 → 单一候选 → 恢复原版复测”排除漂移。正式性能数据只来自官方平台和官方 workload，本机静态检查不得写成运行验证。

3. 展示数值摘要并解释波动、失败请求、异常输出与内存变化。单次峰值只能标为峰值，不能称为稳定吞吐。

4. 给出与文档范围匹配的结论，并把结论映射到代码 commit、正确性结果、MATH-500 Level 3、正式吞吐场景和规则要求。优化成果必须在完成必要验证后明确选择“保留、回滚或否决”；若只能选择“继续验证”，就继续内部实验，不新建成果文档。未完成项在相关结论旁使用 `[待平台验证]`，不另设恢复方法或剩余边界章节。

复现命令必须写明工作目录、环境变量的作用范围、硬件与软件身份、仓库 SHA 以及实际 import 路径，并区分预期结果和实际结果。命令和文档中不得记录密码、私钥、令牌或可复用的访问凭据。市场租赁 C500 可以支撑诊断与预验证结论，但不得由此宣称 C500 或 BI-V150 的正式阶段已验收。正文不得出现实验文件或目录路径、文件链接、SHA-256、日志引用、raw CSV、manifest、trace 或逐题输出位置。

## 5. 命名、维护与验收

`docs/` 中的中文学习资料采用全局唯一的 `SNN-中文主题.md` 编号，`S00-学习索引.md` 固定为索引，后续编号按文档形成顺序递增。`SNN` 只是排序和阅读标识，不等同于七阶段编号；文档在索引中另行注明所服务的阶段。队名、模型名等固有名称可保留原文，生成脚本和正式 PDF 导出件不强制使用学习文档编号。文件重命名后同步更新索引和站内相对链接，不保留指向不存在文档的链接。

每个符合第一节定义的实质性阶段成果使用一份复现文档，同一成果的补充实验、失败分析与官方平台后续验证优先回填原文档。环境打通、单点根因、待验证补丁和“继续验证”实验继续留在内部实验记录中；不得预建占位文件，也不得把每条命令、每轮运行或每个暂时错误切成独立短文。索引在新增成果文档、路径、阅读顺序、阶段或文档状态发生实质变化时同步更新。

文档更新应与工程事实同步。每次服务器实验结束后，在同一工作轮次先同步并核对原始结果，再立即覆盖现有专题中受影响的代码、数值、运行次数和状态；尚无专题时更新现有总方案的当前状态，不为单次实验新建学习文档，也不等到 Git 提交后才补写。完整双场景命令与单场景诊断复测必须分别标明，旧摘要直接替换，只有解释当前结论所必需的历史对比才保留。删除或回滚的优化不能继续出现在最终成果列表中；若失败本身具有学习价值，应说明原因和结果，并标为 `[已否决]`。若同步或文档核对尚未完成，必须如实标明未完成，不能宣称实验闭环。

完成主要文档后按以下顺序验收：

1. 检查白话引言、术语定义、章节深度和段落连贯性，确认零背景读者能沿调用路径理解问题。检查步骤是否疏密适中，代码块后是否立即解释其作用与边界。

2. 检查每个性能或正确性主张是否与官方规则、固定 commit、源码符号和实验结果一致。核对公式单位、假设和换算，确保估算与实测没有混写，同时确认正文没有实验文件、目录、链接、哈希或日志引用。

3. 检查 BI-V150/C500、4K/16K、Prefill/Decode 是否分别呈现，实验身份和状态标签是否完整。最后验证普通站内文档链接、`git diff --check` 和文档索引，但不运行任何项目代码或 GPU 测试。
